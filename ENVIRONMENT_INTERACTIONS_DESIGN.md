# General environment interactions — design and kernel status

Local API investigation, 2026-10-11; pure kernel and backend intent/context/controller integration implemented and tested 2026-10-12. Offline integration uses deterministic AI fixtures. The separate live GPT-6-Luna/UI checkpoint below records actual interpretation and persistence; it does not certify every physical action.

## Implemented kernel and integration contract

`src/environment-interactions.js` exports `validatePropDefinition`, `validatePlan`, `currentSceneSummary`, `propSchema`, `planSchema`, `limits` and async `resolveInteraction({state,adventure,plan,seed})`. New exports in `vendor/dnd-core/entry.ts` expose existing `resolveAttack`, `characterToCombatant`, `setCombatDistanceBand`, `spendObjectInteraction`, `isCharmedBySource`. Build completed. The historical API table below describes the original investigation; functions marked as missing exports are now available through these additions.

Plan fields: `actorId?`, `sourceId?`, `props?` (maximum three), `steps` (one to three). A new prop requires `id,name,locationId,material,size,weightLb,portable`; optional `aliases` (maximum four), `visibility`, `accessible`, `ownerNpcId`, `anchorId` (required by integrated controller). Materials: ceramic/glass/wood/metal/stone/cloth; size: tiny/small/medium/large. The module refuses remote/hidden/inaccessible/heavy/fixed props. Existing ID or matching name/alias cannot create a replacement for a broken prop. Anchors have finite quantity 1-8, default one; materialized props retain originLocationId+anchorId, so broken/held/traveled objects continue to consume their original source count. A plural source permits distinct finite objects; exhausted sources cannot respawn through new IDs or synonyms.

Steps are `{type:take|drop,propId}`, `{type:throw|strike,propId,targetId}` or `{type:check,propId,skill:athletics|acrobatics|sleight_of_hand,difficulty:easy|medium|hard}`. Numerical attack/DC/NPC defaults belong to the server, not the plan. Combat taking/dropping consumes `objectInteraction`, attack/check consumes `action`; wrong actor, incapacity, no budget, total cover, charm source and inappropriate range refuse before committing anything. Throw reach permits engaged/near only; strike permits engaged only. The improvised attack uses STR, no proficiency, 1d4 bludgeoning, a unique exact attack ID and real engine resolution. Taking places a mundane `scene_prop_ID` inventory projection; throwing removes it, drops the same object and breaks ceramic/glass even on a miss. Drop/throw/strike require positive actual inventory projection ownership, so missing/sold projections cannot become virtual weapons. Scene-prop sale is explicitly refused with a natural merchant response and public sellable blocked status. Held objects retain identity across travel when next used. Physical checks synchronize consumed bardic inspiration into combatant.tactics; subsequent normal party synchronization cannot restore the spent die.

On success: `{ok:true,state:newState,adventure:newAdventure,outcome}`. Outcome includes `type`, `sourceId`, mechanical `events`, `text`, `escalation` recommendation with `automatic:false`, optional `stoppedAt/interruption`, and explicit civilian-profile limitation. A failed resolved physical check or a target/actor defeated during earlier steps stops dependent later steps while retaining the real outcomes. On refusal: `{ok:false,state:originalState,adventure:originalAdventure,refusal:{code,message,alternatives}}`; original input objects are never modified. Schema validation rejects unsupported properties/operations. Unexpected runtime programming errors still throw for diagnosis.

Storage is `adventure.environment={version:1,props,npcStates,consequences,appliedPlans}`. An NPC body is keyed by an existing local adapter NPC ID, with bounded civilian defaults HP4/AC10 unless already bound to an actual combat participant. Attack resolution persists body HP/conditions, NPC trust/disposition and one source-linked attempted-aggression consequence per target. No automatic encounter/reward/XP occurs. Plan source ID replay returns the prior outcome without damage or cost; root should pass its operationId as sourceId. Retention limits: 120 props, 80 NPC states, 100 remembered plans, 200 consequences. Broader long-term operation deduplication remains the controller's responsibility.

The integrated controller accepts `type:environment_interaction, plan:{props,steps}` and overrides sourceId/actorId with operationId/current hero. Existing `perform` revisions/dedup remain authoritative. New props must match a current physical affordance by anchorId/material/portability/weight. NPCs outside combat use a deliberately limited civilian body, not complete SRD NPC statblocks. Actual enemy defeat in a pre-existing encounter follows normal `endCombat`, quest victory, XP and one ground-loot record; ordinary civilian attacks never create generated treasure. Persistent NPC-to-new-encounter binding remains future work.

Legacy scenes can establish physical sources lazily in the SAME intent response using `developments.sceneAffordances:[{locationId,sourceText,cues:[{id,description,materials,maxWeightLb,portable}]}]`. It is an additive patch to the existing current location, maximum three new cues and six total, no rewriting. `sourceText` must be an actual substring of current location name/description or a local NPC role. Material/weight constraints are server-checked; semantic plausibility is still the AI-DM's responsibility, and the prompt forbids contrary/exotic/magical sources. Kernel preflight sees the proposed cues on a clone; failed plans discard cues and props together. Narration/inspection may also establish these bounded ordinary sources through normal world developments, without an extra provider call.

`clarify/refuse` replies and kernel refusals become lasting GM messages plus idempotent conversation revision, with no world turn, time, rolls, HP, slots or costs and no extra narration request. Successful physical interaction is one world turn; outside combat it takes six seconds. Dialogue queues invalidate only on actual world actions; existing scene dialogue hooks remain, and proposals use filtered public actions. Public NPC records include body/canInteract; dead/incapacitated targets do not talk/receive delivery/trade. Hostile merchants refuse commerce. Context includes query-ranked visible local/held `sceneProps`, compact NPC HP/conditions/disposition and source cues inside the existing 12,000-character cap.

## Location and model mismatch

Adventure world IDs belong to `adventure.locations` and `adventure.currentLocationId`. Travel changes that ID and `state.openWorld.location` text (`src/adventure-engine.js`, travel branch). It does not synchronize `state.sandboxWorld.currentLocationId` or dynamically register that location as `state.currentScene.id`.

Vendor scene-object resolution uses `currentSandboxLocation(state.sandboxWorld)` and tags facts with `openWorldPlaySceneId`. Adapter `choices()` explicitly filters `open_world.*` (`src/adventure-engine.js:62`). Directly exposing those options would operate on the vendor sandbox, not the player's actual adapter location.

`src/adventure-model.js:10` defines NPCs as name/role/personality/location only. Runtime NPCs add trust/familiarity, with no HP, AC, conditions, disposition or possessions. Existing world items (`:11`) become generated loot on pickup; `adventure.items` is not an environment-object store. `CombatEnvironment` (`vendor/dnd-core/src/core/types.ts:1455`) contains cover/distance/surprise/lair/objective/threat setup but no physical object instances.

`src/adventure-engine.js:187-195` currently maps freeform intent to one command. In combat the prompt requires an exact supplied action ID, and the executor rejects narrative/check/pickup/travel. Thus an unlisted environmental attack cannot be honestly executed by the current flow. Generic exploration `check` only rolls and may add a fact: no prop ownership, target HP or breakage follows from its prose.

## Recommended adapter contract

Keep the existing adapter location ID as the canonical anchor. Add lazily materialized `sceneProps` with stable ID, locationId, name/aliases, bounded material/size/weight, quantity, portable/fixed, ownerNpcId, holderId or ground position, condition (`intact/damaged/broken`), optional object HP, explicit affordances and version. Persist only interacted-with or explicitly established props; do not pre-generate exhaustive rooms. Broken/consumed/held records cannot be rematerialized as fresh props merely because the same noun occurs again.

Add a persistent NPC mechanical record keyed by existing adventure NPC ID: concrete commoner/guard/etc. profile, HP/max/temp, AC, abilities, conditions, life state and hostile/disposition state. Select a bounded default by established role; never silently scale an ordinary bartender to party level. On combat entry bind participant ID to this NPC ID; on every relevant mutation and combat exit synchronize HP/conditions back. Revisiting cannot heal/reset a killed or injured NPC. Separate remembered narrative trust from physical state but have one authoritative trust/disposition source.

AI proposes a finite interaction plan (maximum three dependent operations): `establish_prop`, `take`, `throw/strike`, `manipulate`, `check`, `move`, `social`. These are **proposed primitive names**, not current APIs. Each operation references exact actor/target/prop IDs or an allowed tentative local prop specification. Server resolves aliases within current location, validates plausibility against established scene and material constraints, and computes numerical profile, cost, range, DC and consequences. AI cannot choose arbitrary damage/HP/bonuses, bypass a lock or reinterpret a forbidden move as narrative success.

Refuse or request clarification only for a real unresolved ambiguity/contradiction: no nearby bartender, both mugs behind a locked display, target beyond reach, immobilized/charmer restriction, implausibly heavy prop, spent action. Return concrete reasons and valid alternatives. Missing exhaustive scenery is not by itself a refusal: a mundane portable drinking vessel can be established lazily in an ordinary occupied bar unless current facts contradict it. Do not invent a valuable weapon, key or healing potion from the same premise.

Use one cloned campaign+adventure state for preflight, rules execution, consequences and persistence. Validate deterministic prerequisites for the whole plan before any durable mutation; expected revision and operationId apply to the whole plan. A resolved failed roll is still an executed action: consumes relevant cost, records failure and object landing/consequences. Stop later dependent steps when earlier steps fail; report which steps happened. A malformed/unauthorized plan must not spend anything. Never save `take` then discover `throw` is mechanically invalid; never use successive persistent service calls as an atomic transaction.

`service.store.saveGameState` parses the complete GameState and wraps its SQL changes in `BEGIN TRANSACTION`/`COMMIT` (`vendor/dnd-core/src/core/state/store.ts:59-159`). Persist the final adapter metadata and mechanical state together using the existing adapter `save`. This makes one database write atomic; it does not make several separately saved service calls atomic or automatically serialize concurrent requests.

## Mug example through the generic primitives

1. Resolve existing nearby bartender ID. Resolve established mug or lazily establish one plausible mundane ceramic vessel at the current bar, preserving owner and stable identity. No arbitrary treasure generation.
2. Validate hand/access/portability and actor eligibility. Outside combat, taking an unguarded reachable mug needs no artificial skill roll. Taking from someone's grip requires a real contested/uncertain operation. In combat, a simple pickup uses the free object interaction; throwing uses the attack action. If object interaction was spent, account for a further action and refuse/stage the remainder when the budget cannot fund both.
3. Choose a deterministic bounded improvised profile from material/size (proposal: mundane vessel `1d4` bludgeoning, no proficiency unless an actual feature grants it). Use thrown-weapon STR semantics and explicit short/long reach rules; engine only offers coarse melee/ranged/spell bands, so define a tested adapter range mapping rather than inheriting bow reach. `generatedItemAttack` defaults to DEX for ranged and implicit proficiency, so do not blindly reuse that default.
4. Attack uses a real roll against persistent NPC AC, cover and conditions; a miss deals zero creature damage. A fragile projectile may break on landing regardless of hit; record held→ground/broken and decrement/remove the portable inventory projection once. Stable prop instance is the source of truth; inventory item hashing must not duplicate identity or count.
5. Apply actual HP/temp/conditions using campaign policy, synchronize the NPC, and record hostility/trust loss and local witness response from a bounded generic aggression rule. Misses still constitute attempted aggression. Social consequence is attached to the actor/target/location and event ID, not unsupported narration. Do not auto-charge imaginary fines, auto-kill a surviving NPC, start a fabricated victory reward, or force extra player attacks.
6. For ongoing resistance, transition to an explicit NPC encounter bound to that persistent record. Define whether the opening attack precedes initiative or requires initiative first; test that choice and avoid a free pre-combat attack plus a fresh action from the same input. Ordinary scene attack must not create a generated encounter solely to obtain a damage roller.

## Bounded context and mandatory proof

`src/adventure-context.js` already caps the packet at 12,000 characters, objects at 1,100 characters, NPCs at 1,200 and inventory at 900. Extend compact mechanical prop/NPC entries within that same total cap: current-location entities first, referenced IDs next, only a few relevant nearby props; durable records stay on disk. Include condition/holder/owner/HP/disposition and explicit source (`established`, `materialized`, `proposed`) so prose memories cannot masquerade as proven mechanics. Reuse a persisted prop rather than creating new IDs on retry, revisit or synonymous input.

Implementation proof should include isolated fallback-AI-stub scenarios for: take+throw hit; miss with no creature damage; fragile breakage; revisiting preserves NPC HP/hostility and broken prop; repeat operationId spends/damages once; invalid target/range/budget leaves all state unchanged; unconscious/captured actor blocked; spent object interaction plus remaining action cannot silently do two costs; another player's combat turn blocked; target total cover; ambiguity/refusal with alternatives; thrown stat/proficiency/range; damage concentration and zero-HP outcome; failing precondition/roll stops dependent later steps; Unicode/synonym target resolution; no reward/quest victory for punching a neutral NPC; context cap under many props; same input's attack and initiative never double-grant action. Assertion must inspect slots/budgets/HP/prop state/events/persisted reopen, not merely narration.

## Remaining integration and unsupported behavior

The kernel and backend intent/model/context/controller hooks are integrated and offline tested. Live provider/UI verification of a take-and-throw plan and broken-object refusal is recorded below. Fine-grained hand occupancy including equipped weapons/shields, exact distances in feet and long-range thrown penalties, complete NPC professions/equipment, taking contested possessions from another person's grasp, physical world geometry, anonymous multi-object piles and full social-response simulation remain unsupported. Scene plausibility comes from grounded AI-DM proposals, not proof that every inferred prop was previously observed. Fixed template scene flags, narrative entity registration and `Use Object` messages do not substitute for these mechanisms.

## Live checkpoint, 2026-10-12

In a newly generated bar, ordinary Russian input to take a mug and throw it at the bartender compiled into take/throw without a predefined mug button. A real STR attack rolled 5 against AC10: miss, zero damage. The ceramic mug became broken and left inventory; Mara kept 4/4 HP, gained hostile disposition and trust -20. No civilian XP or victory loot was invented. The action advanced one world turn and six seconds. Attempting to throw the same broken mug was refused with alternatives, without another roll, world turn or time change. Later inspection and conversations used this saved aftermath. Context after inspection: 4,754 characters; seven recorded text requests.

Generated encounters are explicitly refused when they would replace a known NPC by ID or exact normalized name. Full persistent NPC combat, profession-specific profiles, ordinary weapon/spell/item targeting of scene NPC bodies and social restitution remain work ahead. The default civilian body and passive escalation recommendation do not implement automatic retaliation.

## Persistent encounter follow-up — 2026-10-12

The earlier full-NPC-combat limitation is superseded by NPC_COMBAT.md. Known NPC combat commands now route to a permanent encounter, rather than anonymous generated profiles; dead/absent/incapacitated bodies remain refused. New environmental bodies share the same fixed role profile factory as combat. Existing old civilian body stats remain authoritative. Weapons/catalog spells can target these participants in combat; outside-combat spell/object targeting and physical repair remain separate open work.
